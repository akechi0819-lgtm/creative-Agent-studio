# P3 返工复验与护栏排查

日期：2026-10-15。用户要求：复验审核恢复返工，重点找重复确认、过窄限制和正常操作误阻断。本轮是审查，不擅自修改业务合同或应用代码，不新增审批门槛，不推进 P4。

## 结论

原来的“恢复取最早审核”问题已修好；共享选择器由恢复、批准和导出复用，没有新增 UI 确认或额外强制审核。独立重跑 **201/201 测试通过，0 失败、0 跳过**；原两种反例现在分别正确继承 revise 并拒绝批准、继承 pass 并允许批准。隔离生产构建通过，JS 350,654 字节。

但另一条输入变更归档路径仍可能丢掉最后的通过记录，产生错误阻断，需补一个局部修复；Web 应用关闭版 DNA 的按钮也存在误禁用。**P3 仍待这两处功能问题修正与复验。** 重复弹窗和编辑器锁定属于交互减负建议，不单独作为阶段不通过条件。

## 1. 剩余归档问题：最后的通过被去重丢失

`src/creative/tasks.mjs:457—466` 的 `preserveReviews` 仍对审核完整 JSON 做 Set 去重。相同图片的审核依次为 pass、revise、pass，且末条和首条记录完全相同时，归档变为 pass、revise。后续合法复用旧成功基线、局部修改并恢复时，共享选择器只能看到最后的 revise，最终批准被错误拒绝。

主审亲自执行：[archive-review-order-repro.mjs](evidence/p3-independent/archive-review-order-repro.mjs)。临时任务先经公共 `recordReview` 追加决定，**夹具用 `withTask` 对齐末条时间戳以构造完全相同 JSON**；不是宣称自然 API 调用或真实任务已出现该时间戳情形。之后更新需求、显式确认、新制作单、局部修改和恢复均走实际核心路径。输出：v1→v2→v3→v4，审核从 `[pass,revise,pass]` 变成 `[pass,revise]`，恢复决定 revise、批准拒绝，网络调用 0。

这是已有归档语义的残留缺陷，属于中等优先级的错误阻断，不需要重构整个审核系统或新增身份认证。修复应让所有实际归档路径保留有效追加顺序；补充输入变更归档后的端到端回归。保持已有最新决定、版本、页码和 SHA 匹配规则。

## 3. 保留的必要约束

- 请求标识与状态未知时不自动重放，避免重复收费和重复机械操作；用户无需手工填写 UUID。
- 任务版本比较和同任务单入口推进，防止旧指令覆盖新需求；运行时允许阅读，局部草稿可单独放开。
- 成品 SHA、最新审核、选图后撤销旧批准，保证用户批准的是当前图片。
- 用户明确要求局部修改时，当前共享路径已直接使用聊天授权，不再要求整份制作单确认。改后只对发生变化的图片重新审核，最终成品仍由用户批准。
- 重新生成会发新请求的提示有实际用途；可改善呈现方式，不把提醒层层叠加。
