# P3 绘图参考、配置同步与失败重试

日期：2026-10-15。范围：用户已授权的 P3 试用修复；P4 未授权。本文记录实施自验，不代替用户体验复测或独立验收。

## 已核实的问题

1. 旧图片服务多种独立请求返回 HTTP 502，但这不能证明所有部署的服务都不可用。用户换成新图片服务后，直接单图请求返回 HTTP 200，约 23 秒，回收一张 1,059,328 字节 PNG；见 [新服务单图回执](evidence/p3-image-diagnostic/new-upstream-text.json)。
2. 新服务跨域预检仅允许自身域名，而本地 Canvas 来源为 `http://127.0.0.1:59001`。OPTIONS 返回 204 仍会因来源不符被浏览器拦截；见 [跨域预检证据](evidence/p3-image-diagnostic/new-upstream-cors.json)。这是此次 Canvas 秒失败的直接原因。
3. 工作台旧“继续绘图”只恢复查询，遇到已失败的节点仍会结束，未显式要求重新提交。失败页主按钮现改成“重试失败页并继续”，经一次确认传入 `retryPage`。
4. 用户原制作单只有来源 ID，没有每页实际图片引用，因而是纯文字生图。现在每页可选参考图／Logo，保存到制作单版本并真实传图。没有图片时明确显示纯文字生图。
5. 最新聊天失败另有原因：基础模型返回 `413 request body too large`。会话可正常读取；这与此前历史会话结构损坏、以及 Canvas 跨域失败分别记录。见 [413 只读诊断](evidence/p3-image-diagnostic/chat-request-too-large.json)。

## 参考图片与重试验证

每页使用 `referenceImages:[{sourceId,fileOrder}]`，须来自人工保留来源并包含在本页和整单来源 ID 中。执行前核验来源快照、文件类型与 SHA-256。Canvas 同时得到实际图片节点、连线及 composer 图片 token，进入 `/v1/images/edits`；Logo 使用同一传图机制，不擅自借用历史品牌。

真实 Web／Canvas、本地替身上游的浏览器验证通过：两份 PNG 的原始字节哈希与 multipart 中 `image[]` 文件逐一一致，未调用纯文字生成接口；桌面和 390px 页面无横向溢出。见 [参考图证据](evidence/p3-reference-images/verification.json)。第二份图片是本项目应用图标夹具，不代表用户业务 Logo。

另用上游首次 503、第二次成功的夹具验证失败主按钮：确认后请求携带 `retryPage:1`，第二次生成保留两张参考图并完成回收；见 [重试浏览器证据](evidence/p3-reference-images-retry/verification.json)。由此发现并修复恢复时把 Canvas 截短图片摘要当原图核验的问题；现在用 `canvas_read_image` 验证原始字节。长文案摘要携带原内容哈希，恢复时对完整文案校验。

真实双图请求已实际传入新图片服务，约 127 秒后收到 HTTP 524；见 [真实双图回执](evidence/p3-reference-images-live/verification.json)。这次没有成功成品，不能把本地替身成功当作新服务图生图成功。最初 120 秒等待超时的历史记录另存为 `verification-timeout-120s.json`，不覆盖本次上游 524 结论。

## 2026-10-15：图片读取超时边界调查

本轮只读核对未发现 Studio 本地 120 秒图片生成／编辑上限。Canvas 图片 API 的生成、编辑和 Gemini 图片请求由浏览器 Axios 以 600 秒超时保护，并继续传递页面 `AbortSignal`；Supervisor 提供的磁盘构建产物也包含这三个 600 秒调用配置。图片结果及远程图片读取有 600 秒保护。Supervisor 同源转发对生成／编辑 POST 和本次已授权结果图片 GET 设置 600 秒 AbortController，浏览器断开时会取消转发。CLI 任务执行总等待为 600 秒。Node v22.22.3 内置 Fetch 基于 Undici 6.24.1，没有项目自定义 Dispatcher；Undici 文档中的响应头超时和响应体相邻数据块超时默认值均为 300 秒，其中响应体超时按相邻数据块间隔计算，不是整次请求的总时长。仓库中出现的 120 秒值在验证脚本等待窗口或 WebDAV 同步，不是图片生成运行时上限。源码、实际由 Supervisor 静态服务的 bundle 哈希和隔离测试记录在 [本轮超时调查](evidence/codex-real-regression-20261015/timeout-300-investigation.json) 与 [定向测试日志](evidence/codex-real-regression-20261015/timeout-300-tests.log)。

对 `https://zzone.cc.cd/` 的无凭据 HEAD 探测返回 HTTP 200，并带有 `server: cloudflare`、`cf-cache-status: DYNAMIC`，证明该域名当前经过 Cloudflare 边缘代理；这不能读取 zone 当前超时值，也不能单独证明 120 秒错误由哪一跳产生。错误正文若写有 “120-second Proxy Read Timeout”，更可能是远端代理／网关限制；Cloudflare 官方文档列出的常规 Proxy Read Timeout 默认值为 125 秒，HTTP 524 表示代理已连上源站但源站没有及时返回响应。Enterprise zone 可通过 `proxy_read_timeout` 区域设置或符合条件的 Cache Rule 调大，最高 6000 秒；本地 Canvas、Axios 或 Undici 的上限无法覆盖远端边缘代理的限制。参考 [Cloudflare 连接限制与 524 说明](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)、[Cloudflare Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)、[Proxy Read Timeout Cache Rule](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/)、[Cloudflare 区域设置 API](https://developers.cloudflare.com/api/resources/zones/subresources/settings/methods/edit/)、[Node.js Fetch](https://nodejs.org/api/globals.html#fetch) 与 [Undici Dispatcher 超时](https://undici.nodejs.org/api/Dispatcher)。

本地 600 秒上限已经足以等待 2 分多钟；把相关值从 600 降到 300 秒不会解除远端 120 秒代理限制。本轮因此不改图片 API、Supervisor 或 Canvas 的本地超时，不操作上游配置，也不发图片请求。要让此类请求等待超过远端限制，应由图片 API／中转服务的管理员检查该域名所用边缘代理和源站网关的读取超时；若是 Cloudflare zone，先核实 `proxy_read_timeout` 当前值及账户是否允许编辑，再将其设到所需值。若中转后台没有该设置入口，只能由服务提供方或该 zone 的管理员调整。

## 配置同步与同源转发

配置保存后向运行中的本项目 Canvas 推送版本。页面定时、恢复焦点及发起生成前刷新当前会话配置；保存成功与画布同步结果分别呈现，避免保存成功被误认为所有旧标签已同步。已发出的请求不自动重放。

同源转发仅允许当前私有会话所配置的图片服务和 models/generations/edits 路径，使用当前会话密钥、拒绝重定向，不转发到任意地址。凭据、会话 Cookie、bootstrap ticket 和实例 token 不进入日志、证据或导出。

## 后续发现：API 成功但图片未显示

用户在 16:27（上海时间）重试后，中转后台显示成功，但工作台 Job 失败。只读检查当前 Canvas 子图记录为“读取图片失败”，外层被覆盖成“全部图片生成失败”。根线程以同任务文案独立捕获真实响应：HTTP 200、约 25 秒，JSON 约 240 字节，`data[0].url` 存在而 `b64_json` 不存在；独立下载该 URL 返回 HTTP 200、1,365,656 字节 PNG。结构与下载哈希证据见 [返回结构](evidence/p3-remote-image-recovery/response-shape.json)，证据不包含原始下载 URL。

此前真实蓝圆测试覆盖了 base64 返回路径，没有覆盖 URL 返回路径。新同源代理只允许 API 路径，图片存储模块却也会通过它下载结果 URL，因而把生成成功后的取图挡住。修复须同时验证 URL 下载、Canvas Blob 落地、任务回收及 Web 预览，不能以生图接口 HTTP 200 代替成功交付。

现已补齐受控取图：仅允许当前会话下载本次成功生图响应实际返回的 URL，含签名查询参数，不向图片 CDN 发送生图 API 密钥、不跟随重定向。授权仅内存保存，有时限与数量上限。Canvas 聚合节点保留实际读取错误，Web Job 对已识别的本地图片读取失败展示明确提示，不再一律显示“操作未完成”。

修复后以已捕获的真实 URL 响应重放（不再次调用外部生图）：Canvas GET 下载 HTTP 200，原图 Blob 保存和任务回收成功，Web 成品审核页实际图片加载通过，1,365,656 字节及 SHA-256 与独立下载完全一致。见 [完整重放记录](evidence/p3-remote-image-recovery/canvas-replay/verification.json) 和 [Web 可见截图](evidence/p3-remote-image-recovery/canvas-replay/web-image-visible.png)。测试输入文案是隔离夹具，回放的是此前 KET 生成响应；这证明取图链路，不作为夹具文案的生成质量验收。全仓测试 149/149，通过记录见 [最新测试日志](evidence/p3-remote-image-recovery/contract-tests.log)；签名 URL、会话隔离和 CDN 无密钥检查见 [专项证据](evidence/p3-remote-image-recovery/verification.json)。
