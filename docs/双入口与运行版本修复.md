# 双入口与运行版本修复

2026-10-23。根据两份员工证据包返修；不把包内模型自述当成独立证据，不把 CI 通过等同于员工设备验收。原始包包含本机路径和业务信息，不进入公开仓库。

## 已核实的问题和本次处理

- 员工采集的进程命令行仍指向旧安装目录，新构建未运行。本次给源码和运行包启动器加入运行身份：程序根目录、Git 提交（可用时）、发行类型、源码／构建指纹。不同目录、不同构建及无身份的旧实例拒绝复用；新旧快捷方式切换和新版验证后的旧程序删除列为更新验收步骤，见[源码更新与运行核验](源码更新与运行核验.md)及[员工源码更新提示词](员工源码更新提示词.md)。旧版启动器本身不能被新代码隔空改写，必须处理旧入口。
- Web 操作结束时入口锁释放失败会覆盖原操作结果；附件临时目录清理可能使已提交请求以失败结束。本次区分操作结果与清理结果，界面显示清理警告。只允许当前服务持有原释放闭包、原 token／jobId 且无活动作业时重试释放；不重跑创作，不强删其他入口锁。重启后缺少可信释放记录时不在线强解锁，仍走既有恢复流程。
- WorkBuddy 直接执行记录显示脚本先于占用错误；没有进入任务 Canvas。统一为 Web UI 与代理宿主两类入口，代理宿主使用已有共享 CLI、挂载附件、打开任务 Canvas 并读取状态确认就绪；不以任务外脚本或通用诊断画布代替创作。文档规则并非宿主 OS 沙箱，真实宿主遵循情况仍需现场复测。
- 桥接日志只有错误消息，无法定位栈溢出。本次记录时间、请求诊断编号、固定路由／工具名称和去除绝对路径的堆栈文件行列；不记录请求体、图片、凭据、查询串和任意错误消息。CLI／Web 传递诊断编号；已知未连接错误继续分类为未连接。
- 源码审查复现了大节点集合 `Math.max(...nodes)` 的参数栈溢出，改成迭代计算，并用 20 万节点验证。**没有证据表明员工故障就是此输入**；缺失原请求堆栈，原设备栈溢出根因仍未确认。

## 证据包中不能成立的判断

“源码搜不到错误串，所以与产品无关”不成立：源码存在 `ERR_JOB_RELEASE_FAILED`；“进程活着所以任务仍在执行”也不成立。桥接 HTTP 通用错误日志不等于上游代理崩溃。上传临时目录为空不能证明从未接收附件。CLI 当前源码失败设置退出码 1，现场报告的 0 仍需核对实际执行版本和命令包装。

## 内测更新策略

用户明确要求员工端只保留一个有效安装目录和一套入口。新版安装、实际运行身份及功能检查通过后，删除核实属于本项目的旧程序、旧快捷方式和旧下载包，不归档可启动旧版本。API配置、任务、原件和私有数据备份与程序分离并保留；删除前检查路径归属和符号链接，移出用户资料。验证失败则报告未完成，不先删除仍需用于恢复的数据或旧程序。历史源码由Git保留。
