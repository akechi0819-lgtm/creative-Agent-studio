# 独立素材清洗模块

## 能力与边界

`src/assets/cleaner.mjs` 导出 `cleanMaterial({ title, body, files }, { config, signal })`。`files` 必须是绝对路径数组，按传入顺序处理。成功返回原始 `title`、未改动的 `body`、同序 `fileResults`、模型 `summary`、自由标签 `tags: string[]` 和 `promptVersion`。模块只读原件，不写数据库、不复制或改写文件。

当前支持 UTF-8 `.txt` / `.md`、PNG / JPEG / WebP / BMP 图片，以及 PDF。PDF 每一页都由 `pdfjs-dist` 提取文本；同时独立 OCR helper 渲染并识别每一页，结果按页分别保留 PDF 文本和 OCR 文本。图片由 RapidOCR 识别。对不支持的格式、OCR 环境缺失、解析失败、页数不一致或模型响应不完整均返回明确错误；不会跳过文件、限制页数或截断正文。OCR 正常完成但没有识别到文字时，文件记录保留空 `text` 并设置 `warnings: ["no_text"]`；这是合法的无字图片状态，不会伪造 OCR 文本。调用者可以依据用户提供的标题和正文生成候选，品牌或其他图片中无法识别的信息由用户补充。

摘要与标签候选通过一次 OpenAI-compatible `POST {baseUrl}/chat/completions` 请求生成。没有固定业务标签或默认服务地址。`config` 的 `baseUrl`、`model`、`apiKey` 任一为空时返回 `MODEL_NOT_CONFIGURED`，不会发起模型请求；请求不自动重试。超时和网络错误只返回安全错误代码与通用说明，不包含凭据、服务响应正文或 URL。

把标题、正文与所有成功提取的文字发给模型前，调用方应确认服务配置正确。`cleanMaterial` 只使用调用方传入的 `config`，自身不读取配置文件；`scripts/assets.mjs clean` 与独立命令行 `scripts/clean-materials.mjs` 都从 Studio 私有配置读取基础 API。CLI 不再读取 `STUDIO_TEXT_BASE_URL`、`STUDIO_TEXT_MODEL` 或 `STUDIO_TEXT_API_KEY`，也不从输入 payload 读取模型凭据。OCR 在本机执行。

## 命令行

输入 JSON 只包含内容与绝对路径，不放 API Key：

```json
{
  "title": "示例标题",
  "body": "完整正文",
  "files": ["/absolute/path/to/material.pdf", "/absolute/path/to/image.png"]
}
```

先在 Studio 的“模型与服务”中配置基础 API；CLI 会从同一份本机私有配置读取。输入 JSON 不包含服务地址或凭据：

```sh
node scripts/clean-materials.mjs @input.json
```

成功结果写到 stdout；失败时只输出 JSON 错误，不把 Node、Python 或服务端原始诊断写入输出。命令不会落盘输入、结果或凭据。

隔离运行时可用 `STUDIO_DATA_DIR` 指定测试数据根目录；该变量只选择配置和素材数据位置，不承担模型配置。未配置基础 API 时命令返回未配置状态且不发出模型请求。

## 独立 OCR 环境

不要使用旧 RAG-Yuki 的虚拟环境。仓库根目录的 `.venv-ocr` 是本模块独立 Python 环境，并已加入忽略列表。首次准备与运行：

```sh
python3 -m venv .venv-ocr
./.venv-ocr/bin/python -m pip install -r scripts/requirements-cleaner-ocr.txt
export STUDIO_OCR_PYTHON="$PWD/.venv-ocr/bin/python"
node scripts/clean-materials.mjs @input.json
```

直接 OCR 依赖固定为 `rapidocr==3.10.0`、`onnxruntime==1.31.0`、`opencv-python-headless==5.0.0.93`、`pypdfium2==5.14.0`。RapidOCR 官方包使用 Apache-2.0 许可证，ONNX Runtime 为 MIT，OpenCV Python 包为 Apache-2.0，pypdfium2 含 BSD-3-Clause / Apache-2.0 组件与依赖许可证。安装时还会解析这些包所需的传递依赖。

本轮 macOS 验证环境通过清华大学 PyPI 公共镜像 `https://pypi.tuna.tsinghua.edu.cn/simple` 安装。普通安装命令使用当前 pip 索引；helper 的调用协议为：

```text
<STUDIO_OCR_PYTHON> scripts/ocr_materials.py image <absolute-image-path>
<STUDIO_OCR_PYTHON> scripts/ocr_materials.py pdf <absolute-pdf-path> --all-pages
```

图片返回一页 OCR 结果；PDF 返回从第 1 页到最后一页的 OCR 结果。Node 会将 PDF.js 页数与 helper 页数、页序逐项核对。Python 或 RapidOCR 不可用时显式失败。OCR 每个文件默认有 5 分钟超时，模型请求默认有 60 秒超时；调用者可传入 `signal` 取消，命令行收到 SIGINT / SIGTERM 时会取消正在进行的模型或 OCR 子进程。Windows 默认 Python 路径为 `.venv-ocr/Scripts/python.exe`，尚未在 Windows 上验证。超时和取消不会返回部分内容作为成功结果。

## 依赖来源

- Node 侧复用仓库已有 `pdfjs-dist@6.4.299`，用它逐页提取 PDF 文本。上游：[Mozilla PDF.js](https://github.com/mozilla/pdf.js)。
- RapidOCR 使用官方 `RapidOCR` Python API 和 `result.txts`：[RapidOCR 使用文档](https://rapidai.github.io/RapidOCRDocs/main/en/install_usage/rapidocr/usage/)，[安装文档](https://rapidai.github.io/RapidOCRDocs/main/en/install_usage/rapidocr/install/)。推理后端使用 `onnxruntime` 和 `opencv-python-headless`；依赖由 PyPI 项目提供，具体许可证见各项目发布元数据。
- `pypdfium2` 仅负责将 PDF 每页渲染为内存图像交给 RapidOCR，不负责 PDF 文本抽取：[官方 Python API](https://pypdfium2.readthedocs.io/en/stable/python_api.html)。

旧清洗实现只用于复用“正文 + 多图 OCR → 模型自由摘要标签”的流程思路。`cleaner.mjs` 不加载旧代码、环境或配置；模型配置必须由调用方显式传入。新模块不带入旧项目标签、URL、数据归档和业务字段。基础模型来源选择和第三方代码裁剪边界见 [模型来源与裁剪](模型来源与裁剪.md)。

## 验证

测试使用本地假 OpenAI-compatible HTTP 服务，不调用收费服务；覆盖完整长正文传递、逐页抽取、模型错误 / 截断响应、超时、取消及不回显凭据。macOS 独立 `.venv-ocr` 环境已验证 `rapidocr`、`onnxruntime`、`pypdfium2` 导入，并通过两页扫描 PDF 每页 OCR 与无字图片 `no_text` 样本；`node --test tests/cleaner.test.mjs` 为 8/8 通过、0 跳过。没有 OCR 环境时，集成样本会明确标记为跳过；缺失运行时错误仍单独验证。

## 真实历史素材批次

用户指定目录实际有 13 篇，已完整处理 85 个附件（含 PDF 6 页），并用用户明确授权的既有 Grok 4.7 完成摘要与自由标签生成及批量授权入库。产品默认模型配置仍为空。仅测试脚本 `scripts/verify-materials-batch.mjs` 读取用户明确授权的本机配置；它不保存凭据，也不是产品自动选择旧配置的入口。原清洗模型本次 HTTP 401，用户明确改用 Grok 后才继续。结果与质量边界见 [P2实施自验](P2验收.md)。
