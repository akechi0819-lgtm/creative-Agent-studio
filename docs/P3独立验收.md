## 必须修复：恢复图片时取了最早审核

位置：`src/creative/page-edits.mjs:567—570` 的 `latestReviewForSnapshot` 使用 `.find()`；`restorePageEdit` 在约 681—687 行把该记录复制到恢复后的新版本。相比之下，`src/creative/tasks.mjs:957—960` 与最终批准约 1003—1006 行要求同一版本、页码、成品哈希的最新审核为 pass。两处对“最新”的处理不一致。

主审亲自运行的最小反例：[restore-review-repro.mjs](evidence/p3-independent/restore-review-repro.mjs)。执行：

```sh
node docs/evidence/p3-independent/restore-review-repro.mjs
```

脚本只使用虚构任务、临时目录和模拟 Canvas，结束后自动清理，网络与模型调用均为 0。结果为：

| 原图同一哈希的审核顺序 | 恢复后实际继承 | 最终批准实际结果 | 应有行为 |
| --- | --- | --- | --- |
| pass → revise | pass | 接受 | 保留最新 revise，重新复审通过后才允许批准 |
| revise → pass | revise | 拒绝 | 继承最新 pass，不被旧 revise 阻断 |

恢复仍会清空原最终批准，因此这里不是“自动替用户批准”；问题是错误恢复了审核通过条件，后续用户点击最终批准时系统会错误放行。Canvas freshness 只检查当前图像，不能纠正被错误继承的审核决定。Web 与 Codex 共用这个恢复核心，两个入口均受影响。

### 返工和复验要求

统一恢复审核与核心批准对“最新记录”的语义，按版本、页码及图片 SHA-256 继承真正的最新决定；没有有效审核时继续待复审。不得只寻找任意历史 pass，或在恢复时伪造新的人工复审。核对恢复目标页与其他继承页，保留审核历史和明确的最终批准。

增加 pass→revise 与 revise→pass 的回归测试，验证最新 revise 会阻止批准／导出，最新 pass 能按现有合同继续，恢复不影响其他页的成品和最新审核。可使用隔离假图验证，不必再次付费生图。当前反例脚本断言缺陷存在，不能原样运行当作修复通过证据。
