# Company Lite 宿主智能体使用

本项目从 Git 源码目录运行。宿主智能体负责安装准备、Teedy MCP 配置和当前对话创作；本机 Canvas/MCP 是跨线程共享工作空间，保存项目历史、图片与排版状态。需求、材料用途、制作单、确认、实际读图和批准留在当前宿主对话线程，不另建任务或审批系统。

当前支持 Windows 和 macOS；Linux 不支持，也未作适配。历史 CI 曾在 Linux runner 上通过，不代表 Linux 是受支持系统。员工首次安装可使用[宿主中立安装提示词](员工安装提示词.md)；仓库内预置公司 Teedy 与图片 API 默认地址供沿用，员工也可提供其他服务地址。

## 源码准备与依赖

先在宿主中打开克隆后的 Company Lite 仓库根目录，并显式要求智能体从该目录读取 README、AGENTS、本文和创作 Skill。不假定 `.agents/skills` 自动发现；首次使用时从已打开的仓库根目录显式读取。所有命令都从这个仓库根目录运行，不能从 Skill 的文件位置猜项目根目录。

执行 Node 脚本前，宿主先检查 Git、Node.js 22.19+（22.x）或 24+ 和 npm 是否可用。可运行 `git --version`、`node --version` 和 `npm --version`；若 PowerShell 将 `npm` 解析为被策略阻止的脚本，用 `npm.cmd --version` 检查，不要求员工执行 `Set-ExecutionPolicy`。Git、Node.js 和 npm 是源码准备的必要条件；缺少时说明具体缺项，按当前系统官方说明协助安装，不暗改系统策略、权限或 PATH。无需安装 Python、Office 或系统编译器。

首次准备时先读 setup 状态，向员工简洁显示五步进度，再自动运行耗时的依赖安装与 Canvas 编译；完成后重新读状态：

```sh
node scripts/setup.mjs status
node scripts/prepare.mjs
node scripts/setup.mjs status
```

不要在展示初始状态前开始构建。`node scripts/prepare.mjs` 会按锁文件安装或复用固定依赖，并构建 Canvas；`npm run prepare:dev` 是等价开发别名。setup 状态返回实际缺项与下一步，宿主自动检查依赖、准备 Canvas，无需员工手工安装各子项目依赖或编辑配置 JSON。凭据输入方式按当前宿主的实际能力选择；不支持某种方式时换用其他可用的本机安全方式，只有确无可用方式时才报告阻碍。仅在本人登录、使用宿主实际提供的安全凭据入口或需要宿主审批时等待；不把每个步骤变成人工确认。本次安装授权包含一张真实测试图。

## 安装进度

只在首次准备、配置或故障修复时展示以下五项短状态；日常创作不重复安装清单。状态必须来自实际检查或当前宿主的真实工具调用，不将旧报告当作新连接的证据：

1. 环境与依赖。
2. 本地 Canvas/MCP。
3. 素材库 Teedy MCP。
4. 图片 API、连接检查及真实测试图。
5. 完成状态。

可以用简短文本呈现，例如：

```text
环境与依赖：已完成
本地 Canvas/MCP：已完成
素材库 Teedy MCP：当前需本人完成只读登录验证
图片 API、测试图：待进行
完成：待进行
下一步：请在已打开的本机登录页填写公司素材库账号密码；登录后自动验证查询和原件下载。
```

示例只说明显示形式；实际已完成／当前／待进行状态和员工下一步必须按探测结果生成。当前步骤阻塞时只说明本人下一步要做什么。自动推进可执行事项，不要求逐项确认。

新宿主或首次进入新会话时，先确认当前实际可用的 Canvas MCP 工具并调用 `canvas_status`；已保存的检查只代表上次调用。Teedy 状态同样要以当前宿主实际调用现有只读 MCP 为准。日常操作不重跑五项安装清单，也不建立宿主注册或迁移流程。

## 仓库内置默认值

setup 默认读取仓库根目录的 `company-defaults.json`。当前公司配置为：

```json
{
  "image": {
    "baseUrl": "https://api.osodm.com",
    "model": "gpt-image-2.5-sunburst"
  },
  "materials": {
    "baseUrl": "https://teedy.apinova.cn/"
  }
}
```

这些是可更换的非秘密预填值。图片服务优先展示本机已保存的地址和模型，没有时展示默认值，并询问员工沿用还是更换；员工可以在对话提供新的 URL 和模型。使用员工选定值与当前 revision 准备本机配置，不修改仓库默认文件。Key 由所选服务的正式入口取得，通过当前宿主可用的凭据方式输入，不放进普通对话或仓库；不猜测密钥管理页。

## Teedy 素材库

实际认证是 Teedy 的账号密码登录：本机 MCP 请求远端 `/api/user/login`，后续只读请求使用会话 Cookie。旧版本使用本地 Python stdio MCP，并非远端 OAuth MCP；登录 Teedy 网站不会自动授权该进程。Company Lite 复用已验证的只读访问逻辑，以仓库现有 Node 运行时提供 stdio MCP，无需员工另外安装 Python，不改远端内容、标签或 ACL。

所有下列命令由宿主执行，不要求员工打开终端、复制命令或编辑配置。首次连接流程：

1. `setup status` 读取根目录 `company-defaults.json` 中的 `materials.baseUrl`（当前为 `https://teedy.apinova.cn/`）。展示当前素材地址供员工沿用或更换；默认文件缺失时也可接收员工提供的 HTTPS 地址，不能猜测 `/mcp` 或 OAuth 地址。
2. 宿主运行 `node scripts/setup.mjs login-materials <选定的HTTPS地址>` 并保持进程运行，打开命令返回的一次性本机登录链接。重新登录沿用已保存地址时也显式传入该地址，因为未传参数的 CLI 会优先使用公司默认值。员工只在该表单填写本人 Teedy 账号和密码，不发到对话。地址只能监听本机，链接限时有效；不是新的 Studio 设置页面。
3. 表单提交后自动登录、查询前 20 份可读素材，选择不超过 8 MiB 的图片原件实际下载验证。密码错误、无权限、空库或下载失败都不能标记就绪。验证文件只用于连接检查，不自动成为创作参考或进入仓库；通过后凭据保存到本机私有配置，页面显示结果并结束临时登录服务。
4. 宿主运行 `node scripts/materials.mjs mcp-config`，按当前宿主实际格式接入返回的本机 stdio MCP；不会把个人密码写进宿主配置示例。宿主配置可能需要本人批准，以该宿主实际能力为准。
5. 宿主继续实际调用 `search_materials`、`get_material`、`download_file`，检查下载到本机的原件确实存在且非空。安装授权包含一次查询及原件下载验证，无需再让员工逐步确认。测试文件在验证后删除，不加入画布。记录两项结果：

```sh
node scripts/setup.mjs report-host connected search_materials download_file
```

本机自动检查和宿主报告分别记录；旧的单工具报告不能证明原件可下载，也不能使安装完成。新宿主或新会话仍要按实际可用工具重新确认连接。日常创作则保持先选素材再下载原件，不将安装测试的素材视作用户已选参考。

需要重检已保存的凭据时，由宿主运行 `node scripts/materials.mjs check`。登录失效时重新打开一次性登录表单，不让员工转到终端输入。普通问答框会将输入交给模型，不能用来收集密码。

## Canvas MCP

若宿主没有可用的本地 Canvas MCP，从仓库根运行：

```sh
node scripts/studio.mjs mcp-config
```

读取输出中的 `command` 和 `args`，按当前宿主实际接受的 stdio MCP 配置格式添加服务。输出 JSON 外层的 `mcpServers` 是交换示例，不是通用配置文件；本机 MCP SDK stdio 测试不代表任意宿主客户端均已验证。添加后由当前宿主实际调用 `canvas_status`。共享 Canvas CLI 可从源码根运行 `node scripts/studio.mjs status`、`node scripts/studio.mjs open @JSON`、`node scripts/studio.mjs mcp-config`；正常创作优先使用 MCP 工具。

## 图片 API 与私密配置

图片 API 需配置服务 URL、模型和 Key。地址和模型使用员工选择的本机设置或公司预填值，员工也可提供新值；`expectedRevision` 由宿主读取当前 setup 状态后生成。更换中转站时提供新 Key，或由员工明确确认原 Key 在新地址有效，不能默默把旧 Key 发给新服务。`configure-image` 的空 Key 会保留旧值，宿主需按上述选择准备完整参数。项目当前没有图片 Key 专用表单；不要臆造表单、管理页或 CLI 功能，也不要把普通聊天问答框当成秘密输入入口。根据当前宿主的实际能力选择专用凭据入口、本机表单、剪贴板或其他合适的本机安全输入方式。若所选方式不可用，改用其他可用方式；只有确实没有可用方式时才报告阻碍。员工不需要操作终端、理解命令或编辑技术配置。

CLI 当前支持剪贴板和私有 JSON 文件两种可选导入机制。若使用剪贴板，宿主提示员工从公司已提供的入口复制 API Key；只有员工明确确认“已复制这次 Key”后，宿主才可运行以下命令读取一次剪贴板并导入：

```sh
node scripts/setup.mjs configure-image @image-config.json --key-from-clipboard
```

该命令仅读取一次本机剪贴板，把 Key 写入本机私有配置，不回显或写入日志。若宿主提供专用的安全凭据入口且能安全调用现有 `configure-image` 配置协议，可通过该入口接收 Key，并由宿主准备仓库外的本机私有 JSON 文件后使用已有导入命令；这不表示项目新增了 Key 表单或其他 CLI 能力：

```sh
node scripts/setup.mjs configure-image @<本机私有文件>
```

私有 JSON 文件只由宿主在仓库外准备和处理，并限制为当前用户可读写；不得要求员工编辑配置文件，不得打开、输出或记录含 Key 的文件内容。成功导入后删除该临时文件。两种导入方式按实际可用情况选择，不要连续执行两种导入。Key 不得进入普通对话、普通命令参数、仓库或日志。Teedy 账号密码只在上文所述的一次性本机登录表单填写。

配置完成后运行 API 连接检查：

```sh
node scripts/setup.mjs check-image
```

`check-image` 只检查 API 连接，不会生成图片；setup 显示配置 `ready` 也不代表真实测试图验收完成。**本次安装授权包含一张真实测试图，不需要再次向员工确认。**连接检查通过后，由当前宿主通过已接入的 Canvas MCP 提交一次真实生成，使用 `generation_get_status` 查询该节点状态，确认图片实际保存在本机 Canvas 项目历史中，再调用 `canvas_read_image` 读取并检查返回的图片内容。最后用 `canvas_open` 重开对应画布历史，确认项目及测试图可恢复。配置示例、SDK 测试或单独的 API HTTP 200 都不能代替当前宿主实际调用 Canvas MCP、保存图片、读图及重开历史。若生成状态未知，先查询，不要盲目重发可能收费的请求；若返回明确失败，可在本次一张测试图授权范围内修复后再处理。只有连接检查、真实生成状态、图片本机保存、实际读图和历史重开全部成功，图片 API 项才算验收通过。

## 当前线程创作

1. 在当前宿主对话收集目标、受众、规格、文案与品牌要求；关键缺口由智能体向用户询问。
2. 通过当前宿主的 Teedy 只读 MCP 搜索材料并展示候选；用户选择后实际下载原件。记录来源、用途和事实边界在当前对话中，不修改远端内容。
3. 在当前线程整理文案，调用 `company_check_copy` 并传入 `{text}` 对定稿文案做词表提示检查；也可从源码根运行 `node scripts/studio.mjs check-copy @JSON`（JSON 中含 `text`）。检查返回命中词和建议，供宿主与用户判断；它不核验事实、不替代法律审查，也不自动批准或阻止文案。修改文案后重新检查，再展示制作单并取得用户确认。
4. 用户确认制作单且需要画布操作时调用 `canvas_open`，依当前意图选择新项目、最近项目或既有历史项目。只有已实际下载的原件才可用 `canvas_import_file` 导入。
5. 按当前用户授权调用 `canvas_run_generation`；用 `generation_get_status` 查询返回节点。明确失败且仍在原授权和费用范围内时可继续处理；超范围或授权不明时先询问。状态未知先查询，不重复提交收费请求。
6. 提交返回的 `nodeId` 是生成源节点；完成后用 `canvas_get_state`，按本次节点变化及源节点连线找到对应图片节点，再调用 `canvas_read_image` 检查结果；宿主无法查看图片时，不声称完成读图。局部修改后重新读图。用户在当前对话明确批准最终成品后，才用 `canvas_save_image` 导出。

多页制作时，把“页码 → 图片节点 ID”对应关系保留在当前宿主线程，随制作单和读图结果更新。用户只要求修改某页时，只操作该页对应节点；保留原图节点，改版作为新节点记录，并更新对应关系。最终交付时给出定稿文案和各页图片；用户需要 ZIP 时，使用宿主已有的普通文件与压缩能力打包已导出的文件。当前 Canvas MCP 没有 ZIP 导出工具，不增加新的导出平台。

Canvas 保留共享历史与手动绘图。既有像素操作包括导入、拼贴、拼接、组合、裁切、分割、重采样、移动和缩放；旧项目的要求、来源、确认和批准不会自动沿用到当前宿主线程。

## 验证边界

首轮源码根回归 38/38、Canvas bridge 23/23 通过，0 失败、0 跳过；Canvas web typecheck/build 通过。Mac 本机全新浅克隆初始无 `node_modules` 和构建产物，`node scripts/prepare.mjs` 完成三个依赖组安装与 Canvas Agent/Web 构建；克隆目录共享 Canvas 集成 1/1 通过（4.6 秒），覆盖多项目、裁切拼接、历史重启恢复及 MCP stdio 图片读写，未请求生图。setup 最终报告本地源码与 Canvas 就绪，但仍等待当前宿主 MCP。

隔离临时配置下图片服务 `GET /v1/models` 实测 HTTP 200 并列出配置模型；未生图，源配置未改，临时 Key 目录已删除。另一次真实 Canvas MCP 单张生成样本上游 HTTP 200，用时 20.198 秒，本机完整保存用时 25.892 秒，准备画布用时 1.051 秒；主代理已实际打开检查验收图。这只是单次请求样本，不是普遍时延或全宿主验收承诺。源码提交 `5fbf1bd` 的 Windows/macOS/Linux GitHub Actions 已全部通过；具体宿主命令、MCP 图像读取、Teedy 账号与只读权限仍需实际验证。
